# 0034 조회 시점의 팀 순위로 투자자 성과를 계산해요

## 배경

기존 대시보드는 팀이 얼마나 투자받았는지만 보여줘요. 행사에서 좋은 팀을 선택한 투자자도 비교하기 위해 관리자용 개인 성과 조회를 추가해요. 실제 매매 수익이나 잔액을 계산하는 기능은 아니에요.

## 정한 정책

팀 순위별 고정 배점을 사용해요. 투자금 10만원당 1~10등은 +10~+1점, 11~20등은 −1~−10점이에요. 유치액 격차에 비례하는 배점은 인기 팀 집중에 더 큰 보상을 주므로 사용하지 않아요.

조회할 때마다 전체 투자로 팀 배점과 개인 점수를 계산해요. `ALL/PARTICIPANT/STAFF`는 출력 대상과 그룹 내 개인 순위에만 적용하고 생략은 ALL이에요. 미소진자는 점수만 계산해 `rank: null`로 반환해요. 잔액은 응답에 포함하지 않아요. 전액 투자자끼리만 개인 순위를 매기며 동점은 1·1·3이에요.

0원 유치 팀은 꼴찌라는 정책에 따라 성과 계산에서 공동 20등으로 처리해요. 양수 유치 팀은 기존 경쟁 순위를 사용해요. 기존 공개 팀 대시보드는 이 API 추가로 바꾸지 않아요. 투자하지 않은 팀의 배점은 개인에게 직접 적용되지 않아요.

결과 저장·동결·프론트 화면은 추가하지 않아요. 기존 투자 원장·스키마·투자 확정 동작도 변경하지 않아요.

## 읽기 방식과 선택 이유

팀·투자자·원장·버전을 네 번의 일괄 SELECT로 읽고 연결을 반환한 뒤 점수를 계산해요. 인원수만큼 쿼리하는 N+1 방식과 서버 캐시는 사용하지 않아요. 현재 규모는 140명 기준 최소 투자액 10만원을 모두 사용할 때 원장 최대 1,400건이에요.

조회 중 투자가 확정되어도 팀 배점·개인 내역·전액 여부·버전이 서로 다른 시점에서 계산되면 안 돼요. 전용 TransactionTemplate으로 MySQL REPEATABLE READ / SQLite SERIALIZABLE의 새 읽기 트랜잭션을 사용해요. 기존 쓰기 JVM 잠금이나 잠금 SELECT를 사용하지 않아요. 여러 SELECT의 일관성은 실제 DB 동시성 테스트로 확인해요.

근거: [Spring TransactionTemplate](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html), [MySQL consistent nonlocking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html), [SQLite WAL snapshot isolation](https://www.sqlite.org/isolation.html).

## 검증 범위

점수·공동 순위·그룹·미소진 정책의 단위 테스트와, 실제 SQLite·MySQL에서 동일한 API 계약 테스트를 실행해요. DB를 읽는 도중 다른 투자를 커밋해 쓰기가 진행되고 읽기 결과는 동일 스냅샷을 유지하는지 확인해요. 140명·1,400건에서 결과와 쿼리 수를 확인하고 로컬 시간을 기록하되 운영 성능 보장으로 설명하지 않아요.
