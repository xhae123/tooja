# 현재 운영 설정 검토

현재 구성은 한 대의 OCI 인스턴스에서 작은 행사 서비스를 운영하는 구조입니다. nginx가 과도한 요청을 일부 거절하고 앱·DB를 보호하지만, 장애 시 다른 서버가 대신 처리하는 고가용성 구성은 아닙니다.

## 요청이 들어오는 경로

브라우저 → OCI 공개 HTTP 80 → nginx → Docker 내부 tooja:8080 → SQLite.

앱의 8080은 호스트에 공개하지 않습니다. 외부에서 nginx를 건너뛰어 앱에 직접 연결할 수 없습니다. 다른 nginx 서비스까지 제한하지 않고 tooja 설정에만 국가·요청 제한을 적용합니다.

## 제한이 보호하는 범위

| 설정 | 현재 동작 | 보호하지 못하는 것 |
|---|---|---|
| 국가 차단 | DB-IP Lite가 한국으로 분류한 IP만 허용. 알 수 없는 국가도 403 | 한국 VPN, 한국 IP 공격, 국가 데이터 오분류 |
| API 요청 속도 | 로그인 포함 전체 합산 500r/s, burst=1000, 초과 429 | 서버가 500건/초를 처리한다는 보증, API 밖의 모든 요청, 분산 공격의 완전한 차단 |
| 요청 본문 | 기존 기본 1MiB 유지·명시, 초과 413 | 응답 크기, 총 트래픽, 동시 요청 전체 메모리, 작은 고비용 요청 |
| 수신/전송 타임아웃 | header/body 무응답 15초, send 무응답 30초, keepalive 30초, upstream 연결 5초 | 지속적으로 조금씩 보내는 연결의 절대 총 수명 |
| 프로세스 재시작 | Docker unless-stopped로 종료된 컨테이너 재시작 | healthcheck가 unhealthy만 된 상태의 자동 복구, VM 자체 장애 |
| 배포 전 DB 백업 | SQLite backup API로 서버 내부 일관된 백업 | 디스크·인스턴스 손실, 배포 사이에 발생한 변경의 완전한 복구 |
| 앱 로그 크기 | 파일당 10MiB × 최대 3개 | edge nginx 로그, 배포 전 DB 백업 누적 |

3MiB가 안전을 보장하는 특별한 기준은 아닙니다. 이미 1MiB 제한이 있었으므로 '제한이 없으면 3MiB' 요청에 따라 기존의 더 작은 제한을 유지했습니다. 투자 요청 JSON은 아주 작지만, 크기가 작은 요청도 동시에 많아지면 CPU·DB·연결 자원을 소모합니다.

500r/s도 합의한 초기 방어 기준입니다. 1,000건의 순간 초과 여유는 즉시 처리 허용량이지 앱 처리 용량이 아닙니다. nginx 제한의 동작은 격리된 stub upstream에서 검증했고 실제 운영 앱에 5,000건을 보내지 않았습니다. 실제 API 조합으로 수행한 지속 부하/처리 용량 검증은 이번 작업 결과에 포함하지 않습니다.

## 단일 장애점

nginx가 중지되면 외부 요청을 받을 수 없습니다. 앱이 중지되면 요청을 처리할 수 없고, VM이나 SQLite 디스크가 손상되면 nginx가 정상이어도 서비스를 제공할 수 없습니다. 같은 VM에 nginx만 하나 더 둬서는 VM·DB 단일 장애점을 없앨 수 없습니다.

현재는 별도 서버를 추가하지 않고 설정 검사 후 graceful reload, 배포 실패 시 이전 앱 복귀, DB 영속 저장으로 운영 실수를 줄입니다. 무중단 배포를 보장하지는 않습니다. 장애 시 몇 분의 복구 중단도 허용할 수 없는 행사라면 별도 서버·상태 저장소·전환 경로까지 설계해야 합니다.

## 남은 운영 우선순위

1. **HTTPS 전환**: 현재 HTTP이고 Secure 쿠키도 false입니다. CSRF·HttpOnly는 통신 암호화를 대신하지 못합니다. 실제 행사 코드와 세션을 운영하기 전 HTTPS 주소와 APP_ORIGIN, SECURE_COOKIES를 함께 전환해야 합니다.
2. **서버 밖 DB 백업과 복구 연습**: 현재 백업은 같은 디스크에 있습니다. 보관 장소·주기·유실 허용 시간을 정해야 합니다.
3. **DB 백업 보관 정책**: 사용자 요청에 따라 새 배포 성공 후 이전 tooja 이미지·릴리스(JAR·Allure·배포 파일)는 전부 삭제합니다. 현재 버전만 남기고, tooja 전용 빌드 캐시도 비웁니다. 성공 이후의 이전 버전 복귀는 해당 커밋을 CI/CD로 다시 배포해야 합니다. DB 백업은 별도이며 아직 자동 보관 개수 제한이 없습니다. 서버 전체 docker prune은 사용하지 않습니다.
4. **로그와 장애 알림**: 앱 로그에 용량 제한을 넣었지만 기존 edge nginx 컨테이너의 Docker 로그에는 회전 제한이 없습니다. 컨테이너 unhealthy만으로 자동 재시작되지는 않으며, 외부 알림도 별도로 구성하지 않았습니다.
5. **실제 사용 부하 확인**: 서버의 CPU·메모리 강제 한도와 서비스별 동시 요청 제한은 아직 설정하지 않았습니다. 행사장 공용 IP에서 140명 동시 사용 시 응답 시간·오류율·DB 대기를 확인한 뒤 조정해야 합니다.

네 자리 식별 코드는 강한 비밀번호가 아닙니다. 높은 요청 제한과 해외 차단을 적용해도 국내에서의 코드 추측을 완전히 막는 것은 아닙니다. 이는 사용자가 선택한 로그인 정책의 남는 한계입니다.
