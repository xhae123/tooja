# 투자자 성과 순위 API

관리자가 조회할 때마다 현재 팀 순위와 투자 내역으로 개인 점수를 다시 계산해요. **1회 이상 투자하면 순위가 생기고, 투자하지 않은 사람만 순위가 없어요.** 점수는 행사 내 평가 기준이며 실제 손익이나 잔액이 아니에요.

## 요청과 조회 범위

```http
GET /api/v1/admin/investor-rankings
GET /api/v1/admin/investor-rankings?group=PARTICIPANT
```

관리자 세션 쿠키가 필요해요. GET이므로 CSRF 토큰·Origin 헤더는 필요 없고 요청 본문도 사용하지 않아요. 투자 접수 중·중지 중 모두 조회할 수 있어요.

| group | 조회 대상 |
|---|---|
| 생략 또는 `ALL` | 전체 투자자 |
| `PARTICIPANT` | 참가자 |
| `STAFF` | 운영팀 투자자 |

팀 순위와 개인 점수는 **전체 투자 내역**으로 계산해요. 그룹은 목록 대상과 개인 순위에만 적용해요. 같은 사람은 전체 조회와 그룹 조회에서 점수가 같고, 순위는 달라질 수 있어요.

## 점수와 순위

1. 전체 팀의 확정 투자 유치액을 합산해요.
2. 유치액이 많은 순서로 팀 순위를 매겨요. 동점은 `1, 1, 3`이며 같은 순위는 같은 배점이에요.
3. 투자금 10만원당 1~10등은 `+10~+1점`, 11~20등은 `−1~−10점`을 적용해요.
4. 개인이 투자한 각 팀에서 얻은 점수를 합산해요.
5. 선택한 그룹에서 **1회 이상 투자한 사람끼리** 점수 내림차순으로 순위를 매겨요. 잔액이 남아 있어도 포함하며, 개인 동점은 `1, 1, 3`이에요.

예를 들어 2등에 60만원, 15등에 40만원을 투자했다면 `6×9 + 4×(-5) = 34점`이에요.

0원 팀도 평가 대상에 포함하며 **성과 계산에서는 공동 20등(−10점)**으로 취급해요. 모두 0원이면 모두 공동 20등이에요. 실제로 0원 팀에 투자한 내역은 없으므로 해당 감점이 개인에게 직접 부과되지는 않아요. 기존 공개 팀 대시보드의 공동 순위 규칙은 변경하지 않아요.

10만원만 투자해도 순위가 있어요. 점수가 0점이나 음수여도 투자 내역이 있으면 순위에 포함해요. **투자한 적이 없는 사람만 `rank: null`, `score: 0`, `contributions: []`**예요. 관리자는 투자자가 아니므로 제외하고 삭제된 투자자도 목록에서 제외해요. 기존 공개 대시보드처럼 이미 확정된 투자 원장은 팀 유치액에 계속 포함해요.

목록은 순위가 있는 투자자를 먼저, 미투자자를 나중에 보여줘요. 음수 점수 투자자도 미투자자보다 앞에 표시해요. 각 구간 안에서는 점수 내림차순 → 이름 오름차순 → ID 오름차순이에요. 이름·ID는 표시 순서만 정하며 공동 순위를 깨지 않아요.

## 성공 응답

```json
{
  "group": "PARTICIPANT",
  "asOf": "2026-10-27T10:00:00Z",
  "snapshotVersion": 1,
  "count": 2,
  "items": [
    {
      "rank": 1,
      "investorId": "example-invested",
      "alias": "김민수",
      "kind": "PARTICIPANT",
      "teamId": 1,
      "score": 10,
      "contributions": [
        { "teamId": 2, "serviceName": "서비스 A", "teamRank": 1, "investedAmount": 100000, "pointsPerUnit": 10, "score": 10 }
      ]
    },
    {
      "rank": null,
      "investorId": "example-not-invested",
      "alias": "이서연",
      "kind": "PARTICIPANT",
      "teamId": 4,
      "score": 0,
      "contributions": []
    }
  ]
}
```

- `alias`: 사전 등록한 이름. 기존 API의 필드명을 유지해요.
- `rank`: 투자 내역이 있으면 숫자, 없으면 `null`이에요. 투자금을 모두 썼는지 판단하는 용도로 사용하면 안 돼요.
- 개인의 `teamId`: 소속 팀 번호예요. 운영팀 투자자는 `null`이에요.
- `contributions`: 투자 대상 팀별 계산 근거예요. 팀 번호순으로 반환해요.
- `pointsPerUnit`: 투자금 10만원당 배점이에요. 해당 팀 점수는 `investedAmount / 100000 × pointsPerUnit`이에요.
- `asOf`: DB 읽기 스냅샷을 확보한 기준 시각(UTC)이에요.
- `snapshotVersion`: 해당 스냅샷의 기존 투자 데이터 버전이에요. 조회 횟수나 저장한 결과의 ID가 아니에요.
- `count`: `items`의 길이예요. 페이지네이션 없이 선택 그룹 전체를 반환해요.

잔액·지급액·소진 상태·발급 코드는 반환하지 않아요. 대상이 없으면 `200`, `count: 0`, `items: []`예요.

성공 응답은 `Cache-Control: no-store`예요. 결과를 확정·저장하거나 서버 캐시에서 재사용하지 않아요. 조회 도중 새 투자가 들어와도 한 응답의 팀 순위·개인 점수·투자 이력·버전에는 동일한 DB 스냅샷을 사용해요. 다음 조회에서는 새 투자가 반영될 수 있어요.

## 오류 응답

아래 순서로 검사하며 최초 실패를 반환해요. 저장소·실행 예외는 조회 도중에도 발생할 수 있어요.

| HTTP / code | 발생 조건 |
|---|---|
| `401 SESSION_EXPIRED` | 관리자 세션이 유효하지 않으며, 관리자 쿠키가 있거나 반대 역할의 유효 세션도 없어요. 기존 인증 정책과 같아요. |
| `403 FORBIDDEN` | 관리자 쿠키 없이 유효한 투자자 세션만 있거나, 관리자 계정이 비활성 상태예요. |
| `429 RATE_LIMITED` | 직전 60초 동안 같은 관리자 계정의 보호 API 통과 요청이 180회에 도달했어요. `Retry-After` 초 뒤 다시 시도해요. |
| `422 VALIDATION_FAILED` | `group` 이외의 쿼리 키, 쿼리 키 중복, 또는 전달한 `group`이 허용된 세 값과 정확히 일치하지 않아요. 빈 값·공백·소문자도 오류예요. 미입력은 전체로 정상 처리해요. |
| `503 SERVICE_UNAVAILABLE` | DB 읽기 중 저장소 접근 예외가 발생했어요. `Retry-After: 5`예요. |
| `500 INTERNAL_ERROR` | 저장소 예외 외 예상하지 못한 실행 오류가 발생했어요. |

오류 본문은 기존 `error.code/message/details`, `requestId` 형식이에요. DB·계산 실패를 빈 목록이나 0점으로 바꾸지 않아요. WAF 차단 응답은 애플리케이션 오류 형식과 다를 수 있어요.

## 조회 비용과 일관성

투자 버전·팀·활성 투자자·전체 투자 원장을 네 번의 일괄 SELECT로 읽어요. 투자자마다 DB를 왕복하지 않아요. 데이터를 읽은 뒤 DB 연결을 반환하고 개인 점수·정렬을 계산해요. 투자 쓰기의 JVM 공통 잠금이나 `SELECT FOR UPDATE`는 사용하지 않아요.

MySQL은 명시적 `REPEATABLE READ`, SQLite WAL은 `SERIALIZABLE` 읽기 트랜잭션을 사용해요. 한 응답의 여러 SELECT가 같은 스냅샷을 보도록 새 트랜잭션에서 읽어요. 이 API 때문에 다른 읽기·쓰기 API의 트랜잭션 설정을 바꾸지는 않아요.

테스트는 [점수·순위 단위 테스트](../src/test/kotlin/com/tooja/InvestorRankingPolicyTest.kt)와 [SQLite·MySQL API 테스트](../src/test/kotlin/com/tooja/InvestorRankingApiTest.kt)를 봐주세요. Allure에는 각 테스트의 Given·When·Then 단계와 행사 규모 조회의 로컬 측정값을 남겨요. 로컬 측정은 운영 서버 응답 시간의 보장은 아니에요.
